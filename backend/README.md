# КнигоОбмен — backend

Серверная часть проекта «Обмен книгами»: REST API на **FastAPI**, данные
хранятся в **PostgreSQL**, доступ к БД — через **SQLAlchemy**.

Лабораторная работа №2: backend, API и работа с базой данных.

## 1. Структура проекта

Код разделён по назначению, как требует задание:

```
backend/
  app/
    config.py          # 1.3 конфигурация приложения (переменные окружения)
    database.py         # 1.2 подключение к PostgreSQL и сессии SQLAlchemy
    main.py              # сборка FastAPI-приложения, CORS, обработчики ошибок
    exceptions.py         # свои исключения (NotFoundError, ConflictError)
    models/                # 1.1 модели SQLAlchemy (описание таблиц)
      reader.py
      location.py
      book.py
      booking.py
    schemas/                # 1.1 схемы валидации Pydantic (вход/выход API)
      reader.py
      location.py
      book.py
      booking.py
    routers/                 # 1.1 маршруты API — тонкий слой поверх сервисов
      readers.py
      locations.py
      books.py
      bookings.py
    services/                 # 1.2 операции с данными и бизнес-логика
      readers.py
      locations.py
      books.py
      bookings.py
  init_db.py            # создание таблиц и (опционально) демо-данных
  requirements.txt
  .env.example
```

**Почему модели, схемы и роутеры — разные файлы, а не один общий:**
- `models/*` — это то, как данные устроены **в базе** (таблицы, столбцы,
  внешние ключи). Их видит только backend.
- `schemas/*` — это то, как данные выглядят **в API** (что можно прислать
  в запросе, что вернётся в ответе). Например, при создании книги
  (`BookCreate`) нельзя передать `status` — статус всегда выставляется
  автоматически, это уже бизнес-логика, а не поле формы.
- `routers/*` — принимают HTTP-запрос, проверяют, что тело запроса прошло
  валидацию (это делает сама Pydantic-схема), и вызывают нужную функцию
  из `services/*`. Роутеры **не** обращаются к базе напрямую.
- `services/*` — вся логика работы с БД и бизнес-правила (например:
  «нельзя забронировать книгу, если она не в статусе `available`»).
  Сервисы не знают про HTTP вообще — они просто бросают
  `NotFoundError`/`ConflictError`, а `main.py` уже переводит их в
  правильный HTTP-статус.

## 2. Модель данных

Четыре связанные сущности:

```
Reader (читатель)                PickupLocation (точка выдачи)
  id                                id
  full_name                         name
  email (уникальный)                address
                                     hours
       \                            /      \
        \                          /        \
         Booking (бронирование)              Book (книга)
           id                                  id
           book_id       ──FK──▶ books.id      title
           reader_id     ──FK──▶ readers.id    author
           location_id   ──FK──▶ pickup_locations.id   genre
           reserved_on                          year
           due_date                             description
           status (active/overdue/returned)     status (available/reserved/loaned)
                                                 location_id ──FK──▶ pickup_locations.id
```

Связи:
- `PickupLocation` 1 → ∞ `Book` — у одной точки выдачи может физически
  храниться много книг.
- `Reader` 1 → ∞ `Booking` — один читатель может иметь много бронирований.
- `Book` 1 → ∞ `Booking` — у одной книги за время жизни много бронирований
  (история), но не более одной активной одновременно (это уже проверяется
  в бизнес-логике, а не ограничением БД).
- `Booking` дополнительно хранит `location_id` — точку, где книгу нужно
  забрать/вернуть; она берётся из текущего `location_id` книги в момент
  бронирования и не меняется, даже если книгу потом переносят в другую
  точку.

**Почему статус хранится и у книги, и у брони отдельно:** это разные
вещи. `Book.status` отвечает на вопрос «можно ли забронировать эту книгу
прямо сейчас», а `Booking.status` — «что происходит с конкретной
бронью» (она может стать просроченной, при этом книга всё ещё физически
`loaned`).

## 3. Бизнес-логика (что происходит автоматически)

- **Создание брони** (`POST /bookings`): проверяется, что книга и читатель
  существуют, и что книга сейчас `available`. Если да — создаётся бронь
  со статусом `active`, а статус книги меняется на `reserved`. Если срок
  возврата не передан, ставится автоматически +14 дней.
- **Возврат** (`POST /bookings/{id}/return`): бронь переходит в
  `returned`, книга — обратно в `available`.
- **Просрочка**: не хранится "навечно неверной" — при каждом чтении
  бронирования сервис проверяет, не прошёл ли `due_date`, и если да,
  переводит статус в `overdue`.
- **Удаление книги/читателя/точки выдачи с открытыми связями запрещено**
  (например, нельзя удалить книгу, по которой есть активная бронь) —
  чтобы в БД не оставалось "битых" ссылок.

## 4. Валидация и ошибки

Каждая сущность имеет отдельные Pydantic-схемы для создания (`*Create`),
частичного обновления (`*Update`) и чтения (`*Read`) — так входные и
выходные данные не смешиваются.

Примеры проверок:
- Год издания книги — в диапазоне 1400…текущий год (иначе `422`).
- Email читателя — валидный формат и уникальность (иначе `422` / `409`).
- Срок возврата — не может быть в прошлом (`422`).

Соответствие ошибок и HTTP-статусов:

| Ситуация | Статус | Пример |
|---|---|---|
| Неверный формат/значение поля | `422 Unprocessable Entity` | `year: -5` |
| Записи не существует | `404 Not Found` | `GET /books/999` |
| Действие противоречит состоянию данных | `409 Conflict` | бронирование уже занятой книги |
| Всё успешно, тело создано | `201 Created` | `POST /books` |
| Успешно, без тела ответа | `204 No Content` | `DELETE /books/{id}` |

Формат ошибки везде одинаковый: `{"detail": "человекочитаемое сообщение"}`.

## 5. Настройка и запуск

### 5.1. Подготовка окружения

```bash
cd backend
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

### 5.2. Настройка подключения к БД

1. Установите и запустите PostgreSQL локально (или используйте Docker).
2. Создайте базу и пользователя, например:
   ```sql
   CREATE DATABASE book_exchange;
   CREATE USER book_exchange_user WITH PASSWORD 'ваш_пароль';
   GRANT ALL PRIVILEGES ON DATABASE book_exchange TO book_exchange_user;
   ```
3. Скопируйте файл с примером настроек и подставьте свои значения:
   ```bash
   cp .env.example .env
   ```
   Отредактируйте `DATABASE_URL` в `.env` — впишите своего пользователя,
   пароль и имя базы. Файл `.env` не коммитится в git (см. `.gitignore`).

### 5.3. Создание таблиц

```bash
python init_db.py          # только таблицы
python init_db.py --seed   # таблицы + демо-данные (согласуются с frontend-каталогом)
```

### 5.4. Запуск сервера

```bash
uvicorn app.main:app --reload
```

API поднимется на `http://localhost:8000`. Интерактивная документация
(Swagger UI), сгенерированная FastAPI автоматически, доступна на
`http://localhost:8000/docs` — там же можно проверить любой запрос
руками, без Postman.

Проверка, что всё поднялось:

```bash
curl http://localhost:8000/health
# {"status":"ok","environment":"development"}
```

## 6. Основные эндпоинты

| Метод | Путь | Действие |
|---|---|---|
| GET | `/books?genre=&status=&search=` | список книг с фильтрами |
| POST | `/books` | добавить книгу |
| GET / PATCH / DELETE | `/books/{id}` | получить / изменить / удалить книгу |
| GET | `/locations` | список точек выдачи (с числом доступных книг) |
| POST | `/locations` | добавить точку выдачи |
| GET / PATCH / DELETE | `/locations/{id}` | получить / изменить / удалить точку |
| GET | `/readers` | список читателей |
| POST | `/readers` | зарегистрировать читателя |
| GET / PATCH / DELETE | `/readers/{id}` | получить / изменить / удалить читателя |
| GET | `/bookings?reader_id=` | список бронирований |
| POST | `/bookings` | забронировать книгу |
| PATCH | `/bookings/{id}` | продлить срок возврата |
| POST | `/bookings/{id}/return` | отметить книгу возвращённой |
| DELETE | `/bookings/{id}` | удалить бронь |
